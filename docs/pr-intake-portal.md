# بوابة تعبئة ملف الإقامة المميزة — رائد أعمال

صفحة على `/pr-intake` يملؤها العميل بنفسه، بستة تبويبات تطابق نموذج مركز
الإقامة المميزة لمنتج رائد الأعمال. الهدف أن يصل الملف مرتّباً ومصنّفاً
ومعه المرفقات، بدل جمعه من محادثات متفرقة.

## الرابط والوصول

| | |
|---|---|
| المسار | `https://businesspartner.sa/pr-intake` |
| الظهور | **بالرابط فقط** — `noindex`، وليست في `paths` فلا تدخل خريطة الموقع ولا أي قائمة تنقّل |
| الدخول | بريد العميل + رمز تحقق عبر `api/otp.js` — لا رابط سرّي واحد يتشاركه الجميع |

كل عميل يرى مسوّدته هو فقط. الحارس في `link` يرفض أي مسار لا يبدأ بـ
`pr-intake/<uid>/` الخاص بصاحب الجلسة.

## التبويبات الستة

1. **بيانات المتقدم** — التوكيل · الإقامة الحالية والعنوان الوطني · الجواز والاسم الرباعي بالإنجليزي · الحالة الوظيفية
2. **بيانات الأسرة** — التابعون وجوازاتهم وشهادات ميلادهم · التأمين الطبي · خطاب جهة العمل إن كان تابع موظفاً
3. **بيانات الوالدين** — اختياري، بشرط ألا يكونا عاملين في المملكة
4. **البيانات العلمية** — آخر مؤهل صادر فعلاً، وترجمة وتصديق للصادر من الخارج
5. **رائد أعمال** — الفئة · الجهة الاستثمارية بالاسم المرخّص · الحصة *fully diluted* · الرخصة الريادية وبقية المستندات
6. **بيان عام** — أسئلة الإقرار (رفض تأشيرة، قبض، تعثّر مالي…) وملاحظات توضيحية

الحقول المعلّمة بـ`flag` في `TABS` هي التي تُسقط الملفات عادةً، وتظهر للعميل
بتنبيه ظاهر على الصفحة.

## كيف تعمل تقنياً

| الطبقة | الملف | ملاحظة |
|---|---|---|
| الصفحة | `site/assets/data/pr-intake.html` | يَنسخها المولّد كما هي، بنمط `compliance-dashboard.html`. النموذج مبني من مصفوفة `TABS` |
| الخادم | `api/_printake.js` | **مساعد لا دالة** — الاسم يبدأ بـ`_` فلا يُحسب ضمن سقف الـ12 |
| المنفذ | `api/requests.js` | يستقبل عبر `__route=pr-intake`، والتحويل في `vercel.json` |

**المسوّدة ملف JSON واحد** تحت `pr-intake/<uid>/draft.json` في Supabase Storage —
لا جدول جديد ولا هجرة على `db/schema.sql`، ولا صفّ نصف فارغ في نوشن لكل من
يفتح الرابط ولا يُكمل.

**المرفقات** تُرفع base64 إلى `pr-intake/<uid>/<tab>/<طابع زمني>-<اسم>`،
بحد أقصى 8 ميجابايت للملف الواحد و512 كيلوبايت للمسوّدة.

**نسبة الاكتمال تُحتسب على الخادم** لا في المتصفّح، لأنها ما يراه الفريق في
نوشن ويقرّر عليه.

### الإجراءات

| الإجراء | ما يفعله |
|---|---|
| `me` | يُرجع المسوّدة كاملة وقائمة التبويبات |
| `save` | يدمج `body.tabs` **لكل تبويب على حدة** — تبويب لا يمسح غيره |
| `upload` | يرفع مرفقاً ويضيف قيده للمسوّدة |
| `submit` | يسجّل صفّاً في نوشن ويرفع المستندات مرة واحدة، ويحدّث نفس الصفّ في كل تعديل لاحق |
| `link` | رابط موقّع لمرفق — مع حارس المسار |

صيغة `save` و`submit` هي `{ action, tabs: { <tab>: { <field>: value } } }`.
الصفحة ترسل `draft.tabs` كاملة، والخادم يدمج.

## متغيّرات البيئة

| المتغيّر | الحاجة |
|---|---|
| `NOTION_PR_INTAKE_DB` | ✅ معرّف قاعدة «التقديم على الإقامة المميزة — رائد أعمال». بدونه يعمل كل شيء عدا الكتابة في نوشن، ويرد `submit` بـ`notion:false` |
| `BusinessPartnerSiteNotion` | مفتاح نوشن (أو `NOTION_TOKEN`) |
| `SUPABASE_URL` · `SUPABASE_SERVICE_KEY` | تخزين المسوّدة والمرفقات |
| `OTP_SECRET` · `RESEND_API_KEY` | الدخول برمز التحقق |

## التجربة محلياً

```bash
LOCAL_DB=1 npm run build
LOCAL_DB=1 node site/scripts/devserver.mjs
# http://localhost:3000/pr-intake
# الدخول: client@test.local — الرمز 123456
```

المسوّدة والمرفقات تذهب إلى `.localdb/` ولا تلمس Supabase الإنتاج.
الكتابة في نوشن لا تُختبر محلياً لأن المفتاح لا يخرج من Vercel — يردّ
`submit` بـ`notion:false` وهذا متوقّع.

## قبل إرسال الرابط لأي عميل

عبّئ ملفاً تجريبياً كاملاً على الإنتاج وتأكد أن الصفّ وصل نوشن **ومعه
المرفقات**. هذه هي الحلقة الوحيدة التي لا يمكن التحقق منها محلياً.
