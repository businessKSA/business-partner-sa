# مسوّدة: بوابة الشريك داخل `/my` على التصميم الجديد

**الحالة:** مسوّدة للنقاش — لا بناء قبل موافقة المالك (2026-10-29).
**الوكيل:** `suppliers-partners` (المحتوى والمنطق) + `client-portal` (الدخول والقشرة) بحسب قاعدة «إيجنت مع لوحتها».
**الأساس:** قرار 2026-09-24 يمنع تطوير `/partner-dashboard` و`/suppliers-admin` القديمتين؛ الميزة تُبنى في الجديد.

## 1) ما يوجد اليوم (من `api/_suppliers.js` و`site/assets/js/main.js`)

| الوظيفة | المسار الحالي | ملاحظة |
|---|---|---|
| تسجيل + رمز بريد 6 أرقام (15 د) | `POST type:signup` ← `verify-email` ← `resend-code` | الرمز بلا جدول: HMAC يعود للمتصفح |
| دخول بكلمة مرور / Google | `type:login` / `type:google` | لا جلسة: البريد وكلمة المرور تُرسَل مع **كل** طلب |
| أوامر العمل | `GET ?action=orders` | |
| تحديث الحالة ورفع فاتورة المورّد | `type:order-update` | |
| عرض السعر | `GET ?action=quote`، `type:rfq`/`award`/`quote-decision` | |
| العقد والتوقيع | `?action=contract`, `sign-start`, `sign-submit`, `contract-send` | |
| محفظتي | `GET ?action=wallet` | المحتجز + الرصيد + آخر 20 حركة |
| تسليم الضمان / موافقة الإرجاع | `type:escrow-deliver` / `escrow-agree-refund` | |
| سحب | `type:withdraw` | يرسل بريداً للفريق؛ التحويل والتسجيل يدويان |
| خدماتي وأسعاري / اقتراح خدمة | `my-services` / `propose-service` | |
| فاتورة العمولة | `type:invoice` (للمالك)، `daftra-commission` | الافتراضي 20% ويُعدَّل لكل مورّد |

التخزين: Notion «Suppliers» و«Supplier Orders» للسجل والأوامر؛ Supabase للضمان (`escrows`) والمحفظة (`supplier_wallet_transactions` + العرض `supplier_wallet_balances`).

## 2) الشاشات المقترحة في `/my` (دور «شريك»)

1. **نظرة عامة** — حالة الاعتماد (جديد/معتمد/موقوف)، أوامر تنتظر إجراءً، رصيد متاح، محتجز.
2. **أوامر العمل** — قائمة + تفصيل: الحالة، عرض السعر، العقد، رفع الفاتورة.
3. **الضمان والمحفظة** — محتجز لي، «سلّمت العمل»، موافقة على الإرجاع، الحركات، طلب سحب.
4. **خدماتي وأسعاري** — خدمات الكتالوج وعمولة كل خدمة، واقتراح خدمة جديدة.
5. **ملفي** — بيانات الشركة، السجل التجاري والرقم الضريبي، وكلمة المرور.

المبدأ: كل شاشة تُبنى بـ`SV1.shell()` وبنمط `simple-v1-my.mjs`؛ وقسم الشريك يملكه `suppliers-partners` محتوىً ومنطقاً، و`client-portal` يملك الجلسة والشريط الجانبي.

## 3) ما يُعاد استعماله وما ينقص

**يُعاد استعماله كما هو:** منطق أوامر العمل والعروض والعقد، `ordersForSupplier`، حساب العمولة والفاتورة (`daftra-commission`)، جداول الضمان والمحفظة وعرض الرصيد، منطق `withdraw` وبريده.

**ينقص (يحتاج قراراً أو بناءً):**
- **جلسة للشريك.** اليوم لا رمز جلسة؛ كلمة المرور تُرسَل بكل طلب وتُخزَّن في المتصفح، وفي `GET` تظهر في الرابط (`pw=`). الجديد يحتاج جلسة موقَّعة قصيرة العمر. هذا شرط مسبق لأي شاشة.
- **ربط هوية الشريك بنظام `/my`.** `/my` مبني على حساب العميل والمنظمة (Supabase)؛ الشريك سجلّه في Notion بلا `organization_id`. القرار: دور «شريك» على حسابات `/my` الحالية، أم هوية منفصلة؟
- **محفظة الشريك مقابل محفظة العميل.** `wallet_accounts` للعميل، و`supplier_wallet_*` للمورّد بلا مفتاح منظمة — يلزم توحيد أو فصل صريح.
- **السحب آلي.** اليوم بريد ثم تسجيل يدوي من `/admin`. الجديد: حالة طلب سحب (مقدَّم/مُنفَّذ) وسجلّها.
- **الضمان من جهة المالك.** لا نظير في `/ops` لتسجيل السحب وقرارات النزاع (تُقرَّر اليوم من `/admin ← الأدوات`).
- **لوحة اعتماد الشركاء** (`/suppliers-admin`) تنتقل إلى `/ops` كقسم لـ`owner-ops`.
- **الاسم والحالة:** `suppliers-partners` يمسّ `/ops` و`/my` — كلاهما ملف `client-portal`/`owner-ops`؛ يلزم تنسيق قبل الكتابة.

## 4) ترتيب بناء مقترح (بعد الموافقة)

1. جلسة الشريك + واجهة الدخول (يتقاطع مع `client-portal`).
2. نظرة عامة + أوامر العمل (قراءة فقط).
3. الضمان والمحفظة (+ حالة السحب).
4. خدماتي وملفي.
5. قسم اعتماد الشركاء في `/ops`، ثم إغلاق `/partner-dashboard` و`/suppliers-admin` القديمتين بتحويل.

## 5) قرارات تحتاج المالك

- دور «شريك» داخل حسابات `/my` أم هوية منفصلة؟
- هل يُؤتمت السحب (تحويل بنكي) أم يبقى يدوياً بحالة متتبَّعة؟
- متى تُغلَق اللوحتان القديمتان بعد النقل؟
