# النشر إلى الإنتاج

## قائمة التحقّق — لا تُتجاوَز

### ١. دور قاعدة البيانات لا يتخطّى العزل

**هذا أخطر بند في القائمة، وأصمتُها فشلاً.**

```sql
SELECT rolname, rolsuper, rolbypassrls FROM pg_roles WHERE rolname = current_user;
-- يجب أن يكون العمودان الأخيران f و f
```

إن كان أيّهما `t`:

```sql
ALTER ROLE "<الدور>" NOSUPERUSER NOBYPASSRLS;
```

ويبقى الدور **مالكاً** للجداول ليقرأها ويكتبها ضمن السياسات.

#### على Supabase: الرابط الافتراضي يتخطّى العزل

تحقّقنا من هذا على مشروعٍ حيّ، فليس تحذيراً نظرياً:

| الدور | `rolsuper` | `rolbypassrls` |
|---|---|---|
| `postgres` — **الرابط الذي تنسخه من اللوحة** | `f` | **`t`** |
| `service_role` | `f` | **`t`** |
| `supabase_admin` | `t` | `t` |
| `authenticator` / `anon` | `f` | `f` |

فلا يُستعمل رابط `postgres` للتطبيق. أنشئ دوراً مخصّصاً مرّةً واحدة:

```bash
psql "$ADMIN_DATABASE_URL" -f scripts/bootstrap-role.sql
```

ثم اجعل `DATABASE_URL` بالدور `erp_app`. وشرحُ السبب كاملاً في رأس ذلك
الملف. لا تُعدّل `postgres` نفسه بـ`NOBYPASSRLS` — تعتمد عليه خدمات
Supabase الداخلية.

لماذا هذا البند أولاً: Postgres يعفي السوبريوزر وحاملَ BYPASSRLS من سياسات
الصفوف إعفاءً تاماً. السياسات تبقى معرَّفةً في الجدول ولا تُطبَّق. فلو وصل
التطبيق بدورٍ كهذا لصار كل عملاء المنصة في دفتر واحد — ولا شيء في الشاشة
ولا في السجلّات يشي بذلك. `npm run db:push` يفحص هذا ويرفض المتابعة، فلا
تتجاوزه يدوياً.

### ١·٥. حساب مالك المنصة لا يُزرع بكلمة سرٍّ من المستودع

`prisma/seed.ts` يحمل بريداً وكلمة سرٍّ ثابتين للتطوير المحلي. وفي أي
بيئةٍ منشورة تُضبط من البيئة:

```bash
SEED_OWNER_EMAIL="you@example.com"
SEED_OWNER_PASSWORD="$(openssl rand -base64 18)"
```

والبذرة **ترفض العمل** بدونهما متى وُجد `VERCEL` أو `SEED_REQUIRE_ENV=1`،
وترفض كلمة السر المكتوبة في المستودع صراحةً. السبب: لوحة المنصة تُنشئ
منشآت العملاء وتحذفها، فكلمةُ سرٍّ يعرفها كل من قرأ المستودع تعني أن
دفاتر كل عميلٍ في متناول أي قارئ.

### ١·٧. مشروع Vercel يبني كل فروع المستودع — لا فرع الـERP وحده

المستودع واحد وفيه ثلاثة مشاريع Vercel (الموقع التسويقي، وعروض الأسعار،
والـERP)، وكلٌّ منها **يُبنى عند كل دفعة على أي فرع**. فدفعةٌ على فرع
الموقع التسويقي تُطلق بناءً للـERP لا معنى له.

ولهذا في `vercel.json`:

```json
"ignoreCommand": "git diff --quiet HEAD^ HEAD ./"
```

يُنفَّذ من جذر المشروع (`erp/`)، فيخرج بصفر — أي «تخطَّ البناء» — حين لا
تمسّ الدفعةُ هذا المجلّد، وبواحد فيُبنى حين تمسّه.

واتجاه الخطأ فيه مقصود: أي فشلٍ في الأمر نفسه يُعيد رمزاً غير الصفر،
فيبني Vercel. أسوأ ما يقع بناءٌ زائد، لا نشرةٌ تُمنع صامتةً.

**وانتبه:** الملف يُقرأ من الدفعة التي تُبنى. فالفروع التي تفرّعت قبل
إضافته لا تعرفه، وتظلّ تُبني الـERP بإعداد جذر المستودع وتفشل حتى تُدمج
أو تُحدَّث من `master`.

### ٢. الأسرار

```bash
openssl rand -base64 32   # SESSION_SECRET
openssl rand -base64 32   # ENCRYPTION_KEY
```

`ENCRYPTION_KEY` يشفّر مفتاح توقيع فواتير زاتكا ورموز الشهادات. **فقدانه
يعني فقدان القدرة على إصدار فواتير باسم المنشأة** حتى يُعاد الربط من أوّله.
احفظه في خزنة أسرار، واحفظ نسخته الاحتياطية، ولا تغيّره بعد أول ربط.

### ٣. الاتصال المشفّر

الجلسة تُرسل كوكيزاً بعلَم `Secure` في الإنتاج، ولا تصل عبر HTTP.

### ٤. النسخ الاحتياطي

```bash
pg_dump --format=custom --file=erp-$(date +%F).dump "$DATABASE_URL"
```

يومياً على الأقل، مع اختبار استرجاعٍ شهري. نسخةٌ لم تُختبر استعادتها ليست
نسخة احتياطية.

### ٥. الفحوص بعد كل نشر

```bash
npm run health   # سلامة الدفاتر
npm run e2e      # اختبار دخان بمتصفّح حقيقي
```

## القياس والحدود

**زمن المعاملة.** `withTenant` يفتح معاملة لكل طلب. الافتراضي ١٥ ثانية،
والعمليات الثقيلة (مسيّر رواتب، تجهيز منشأة، إرسال زاتكا) تمرّر مهلة أطول
صراحةً. المهلة القصيرة تقطع عملية في منتصفها، والطويلة تحجز اتصالاً من
المجمّع — كلاهما يظهر تحت الحمل لا في التطوير.

**تجميع الاتصالات.** استعمل PgBouncer بوضع `transaction`. سياق المنشأة
يُضبط بـ`set_config(..., true)` أي محلياً للمعاملة، فهو متوافق مع هذا
الوضع ولا يتسرّب بين الطلبات.

**التقارير.** كلها تُقرأ من `JournalLine` بتجميعٍ في Postgres. الفهارس
القائمة تكفي لملايين السطور. حين لا تكفي فالحلّ لقطةٌ مؤرَّخة
(materialized view) تُحدَّث بجدول — لا جدول أرصدةٍ يُحدَّث مع كل حركة،
فجدولٌ كهذا ينحرف يوماً عن الدفتر ثم لا يُعرف أيّهما الصادق.

## ما ليس فيه بعد

قيلت صراحةً كي لا تُكتشف في الإنتاج:

- **لا سحب آلي لكشوف الحساب من البنك.** التسوية البنكية مبنيّة
  (`src/lib/treasury/reconciliation.ts`): يُستورد الكشف ملفَّ CSV، ويقترح
  المحرّك المقابلات بدرجة ثقة، ويُقفل الكشف بعد تفسير كل بند. لكنّ جلب
  الملف من البنك يدويّ — لا واجهة برمجية مصرفية موصولة.
- **لا تطبيق جوال.** الواجهة تستجيب للشاشات الصغيرة ولا تطبيق أصلياً لها.
- **الفوترة الإلكترونية لم تُختبر على بيئة الهيئة.** راجع `zatca.md`.
