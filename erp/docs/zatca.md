# الفوترة الإلكترونية — هيئة الزكاة والضريبة والدخل

## ما هو مُنفَّذ ومُتحقَّق منه

| الجزء | الحالة | كيف تُحقِّق منه |
|---|---|---|
| ترميز TLV لرمز QR | ✅ متحقَّق تحققاً تاماً | حالة الاختبار الرسمية المنشورة في وثيقة الهيئة تُنتج الرمز المنشور حرفاً بحرف — `tests/zatca-tlv.test.ts` |
| صيغة التجزئة | ✅ متحقَّق تحققاً تاماً | القيمة الابتدائية للسلسلة تُشتقّ حسابياً وتطابق المنشور — `Base64` للنصّ الست عشري لا للبايتات |
| طلب توقيع الشهادة (CSR) | ✅ متحقَّق باستقلال | `openssl req -verify` يقبله، والمنحنى `secp256k1`، وامتداد القالب والاسم البديل بحقوله الخمسة موجودة |
| بنية UBL 2.1 | ✅ سليمة نحوياً | `xmllint` يحلّلها، وترتيب العناصر يتبع المخطط |
| حذف العناصر الثلاثة قبل التجزئة | ✅ متحقَّق | اختبار يؤكّد أن حقن التوقيع وQR **بعد** التجزئة لا يغيّرها |
| التوقيع ECDSA-SHA256 | ✅ متحقَّق رياضياً | التوقيع يُتحقَّق منه بالمفتاح العام للشهادة، وتغيير حرف في الفاتورة يكسره |
| تشفير المفاتيح المخزَّنة | ✅ متحقَّق | AES-256-GCM، والعبث يُكتشف عند الفكّ |

## ما ليس مُتحقَّقاً منه — واقرأ هذا قبل الإنتاج

**قبول الهيئة لهذا التوقيع بعينه لم يُختبر، ولا يمكن اختباره محلياً.**

سببه أن ثلاثة أمور لا تُحسم إلا بتشغيل حقيقي ببيانات ربط حقيقية:

1. **تقنين XML (C14N).** المواصفة تنصّ على `xml-c14n11`. مولّدنا يُخرج
   شجرةً قانونيةً بالبناء (وسوم فتح وإغلاق دائماً، سمات مرتَّبة، بلا
   مسافات بين العناصر)، وهو مكافئ للتقنين على المستندات التي نولّدها نحن.
   لكن أداة الهيئة قد تُقنّن بمسافات بادئة مختلفة، والفرق في بايت واحد
   يغيّر التجزئة.

2. **تجزئة الخصائص الموقَّعة.** استعملنا صيغة الهيئة نفسها
   (`Base64` للنصّ الست عشري) اتّساقاً مع تجزئة الفاتورة. بعض التطبيقات
   تستعمل `Base64` للبايتات الخام هنا. الاختيار معزول في دالة واحدة
   (`sha256Zatca` في `hash.ts`) فتغييره سطرٌ واحد.

3. **ترتيب حقول اسم المُصدر.** نعكس أسطر Node لنحصل على الترتيب المعتاد
   في X.509. صيغة الهيئة المتوقَّعة قد تختلف.

## خطوات التحقق قبل الإنتاج

```bash
# ١. ولّد المفتاح وطلب التوقيع
npm run zatca:csr -- --tenant <slug> --env SANDBOX

# ٢. خذ رمز التحقق (OTP) من بوّابة فاتورة — صالح ساعة واحدة
# ٣. اطلب شهادة الامتثال
npm run zatca:onboard -- --tenant <slug> --otp <رمز>

# ٤. شغّل اختبارات الامتثال: فواتير نموذجية بكل نوع ستُصدره المنشأة
npm run zatca:compliance -- --tenant <slug>

# ٥. عند نجاحها اطلب شهادة الإنتاج
npm run zatca:production -- --tenant <slug>
```

إن رُفض في الخطوة الرابعة، فالرسالة العائدة من الهيئة تقول أي حقل
اختلّ. المواضع الثلاثة أعلاه هي أول ما يُراجَع.

## قرارات معمارية

**لماذا كُتب التنفيذ من الصفر بدل استعمال أداة الهيئة؟**
أداة الهيئة الرسمية مكتوبة بلغة جافا. ربطها بنظام TypeScript يعني تشغيل
جهاز جافا افتراضي بجانب كل نشر، وزيادة زمن الإقلاع، وتبعيةً ثقيلة في
مسارٍ يجب أن يبقى مقروءاً. ما نحتاجه منها — ترميز DER لطلب التوقيع،
وTLV، وتجزئة، وتوقيع ECDSA — ثلاثمئة سطر مقروءة ومُختبَرة.

**لماذا تُثبَّت التجزئة في السلسلة بعد القبول لا قبله؟**
لأن تثبيتها بعد رفضٍ يجعل الفاتورة القادمة تشير إلى فاتورة لا وجود لها
لدى الهيئة، فتُرفض هي الأخرى، وهكذا حتى يتعطّل الإصدار كلّه. الرفض
يُبقي السلسلة على حالها فتُعاد المحاولة بالموضع نفسه.

**لماذا يُفرَّق بين «مقبولة بملاحظات» و«مرفوضة»؟**
الحالة ٢٠٢ تعني أن الفاتورة **نافذة** والملاحظات تُعالج لاحقاً.
معاملتها كفشلٍ تجعل النظام يعيد الإرسال، وإعادةُ إرسال فاتورةٍ قُبلت
تكسر العدّاد وتُنتج تكراراً في سجلّ الهيئة.
